## 四项并发改动

1. 领码按手机号和 IP 共同限流：单人电话每分钟 5 次；同号多人时电话总额度为人数 × 10，同一电话＋姓名每分钟 5 次；每 IP 默认 600 次，可用 `TICKET_IP_LIMIT` 调整。计数通过共享数据库的一条 SQL 原子更新，同一 Wi-Fi 的不同来宾不会共用原先 20 次的低配额。超限返回 429 和重试时间。

## 发布顺序

- 先确认云托管环境正常、套餐资源充足。主环境的有效期不能证明云托管资源可用。
- 保留现有 `CLOUDBASE_ENV_ID`、`CLOUDBASE_API_KEY`、管理密码和域名/代理配置。HTTP 数据库通道无需设置 `DATABASE_URL`。凭据只通过云托管环境变量传入。
- 在已注入目标环境凭据的运维进程运行 `npm run db:migrate`。CloudBase 每次只执行一条 SQL，不能跨 HTTP 请求持有事务或迁移锁。迁移成功后部署时设置 `DB_MIGRATE_ON_START=0`，避免多个容器同时执行 DDL。
- 使用根目录 Dockerfile 部署同一 `meetin-checkin` 服务，设置 `APP_REVISION`。检查新版本状态及线上 `/api/health` 标记后，执行登录、领码、并发重复签到和统计验证。
- 服务实例数和 `DB_HTTP_MAX` 一起决定 SQL 在途请求上限：若仍为最多 2 实例、每实例 8 条，则正常运行最多约 16 条在途 SQL；滚动发布期间还需给旧实例留余量。这个数不代表可承载用户数或每秒签到数，需按实际数据库延迟压测。
- 保留至少一个常驻实例可减少冷启动，也会持续消耗套餐资源。扩大实例数前先确认资源预算。

`npm run db:cleanup` 只清理过期超过 24 小时的限流记录。建议在外部运维任务中每日执行；本次没有创建云端定时任务。
